## 1. Root Cause Analysis with Evidence

### Evidence from Adrian's System (Brief 010)
- In-app update from v0.12.0 to v0.12.1 was executed at **18:04:44** (`Programs\AppLoad\appload.exe` replaced, `appload.exe.old` = v0.12.0).
- At ~**18:05**, Adrian deleted `"Kafka Provisioner – production v1.0.0 (Failed 2026-10-30)"` (`id: 63047f4e-d980-4a9d-8a19-286204c674eb`).
- The success toast `"Deleted deployment record v1.0.0 (Kafka Provisioner - production)"` was displayed (in v0.12.1 this strictly requires SQLite `rows_affected == 1`).
- Yet inspecting Adrian's DB copy showed both v1.0.0 rows present (`91411f7d…` and `63047f4e…`, total 165 rows) with DB mtime **18:05:10**.

### Hypothesis Evaluation & Proof

| Hypothesis | Verdict | Evidence |
|------------|---------|----------|
| **1. Old-process write-back after in-app update overlap** | **PROVEN (Root Cause)** | In `v0.12.0`, `restart_application()` spawned the updated `appload.exe` immediately without waiting for the old process to exit. Furthermore, `v0.12.0` had no single-instance mutex. The old `v0.12.0` process remained alive for several seconds during graceful shutdown / background sync. In `v0.12.0`, saving state used `save_all_to_db` (which executes `DELETE FROM deployments` followed by inserting all 165 records from in-memory RAM). At **18:05:10** (26 seconds after update spawn), the lingering `v0.12.0` process flushed its stale in-memory state back to SQLite, completely overwriting the database and resurrecting the row deleted by `v0.12.1`. |
| **2. In-process re-insertion by v0.12.1** | **DISPROVEN** | Verified in sandboxed reproduction test `test_repro_010_inspect_kafka_coordinates_and_kittest_delete`. In a single-process run of `v0.12.1` using a copy of Adrian's exact 165-record database, deleting `63047f4e…` immediately reduced the database to 164 rows (`rows_affected == 1`). Running 60 consecutive sync cycles (simulating 2 minutes of periodic background sync checks) never resurrected the row. A full application restart loaded 164 records with `63047f4e…` permanently gone. |
| **3. ID mismatch between UI and record** | **DISPROVEN** | Confirmed that `delete_target` passed the exact clicked `dep.id` (`63047f4e-d980-4a9d-8a19-286204c674eb`), and SQLite reported `rows_affected == 1`. |

## 2. Multi-Layer Defenses & Review Follow-Up

Following Orchestrator review, a critical update-restart scenario was addressed:
Because `v0.12.1` and `v0.12.0` relaunched the new binary without `--wait-for-pid` and the old lingering process could take up to ~26s to flush and exit, a flat 5s wait would cause the new instance to time out and exit, leaving the user with **no AppLoad running**.

The multi-process guard was upgraded with parent process detection and adaptive wait:

### Layer 1: Parent Process Detection & Adaptive Wait (`src/single_instance.rs` & `src/main.rs`)
- Uses Windows `CreateToolhelp32Snapshot` (`TH32CS_SNAPPROCESS`) inspecting `th32ProcessID` and `th32ParentProcessID`.
- Detects running instances of `appload.exe` and `shiply.exe` (with strict `APPLOAD_SANDBOX_ROOT` scoping to never inspect or interact with host desktop processes).
- **Update Restart (Parent Instance / `--wait-for-pid`):** If any running instance is our parent process (or `--wait-for-pid` was specified), AppLoad recognizes it as an in-app update transition and waits **up to 90 seconds** for the old instance to terminate.
- **Genuine Second Launch (Non-Parent Instance):** If another instance is running but is not our parent, AppLoad waits only **5 seconds**, then focuses the existing window and exits cleanly.
- **Waiting Splash Window:** If waiting exceeds **2 seconds**, AppLoad shows a native topmost splash box:
  `"Finishing update — waiting for the previous AppLoad window to close…"`
  The window automatically dismisses as soon as the old instance terminates. In sandbox test mode, it logs to stderr without popping windows.
- **Clear Dialog on Timeout:** If the 90s update restart timeout expires, AppLoad shows a clear native message box dialog:
  `"Another AppLoad is still running. Close it and start AppLoad again."`
  instead of silently disappearing. (In sandbox mode, logs without blocking).

### Layer 2: Post-Update Old PID Handshake (`src/updater.rs` & `src/main.rs`)
- Added `--wait-for-pid <PID>` CLI option.
- When `restart_application()` relaunches the updated executable after an in-app update, it passes `--wait-for-pid <current_pid>`.
- The new process synchronizes startup and waits for the old PID to terminate before opening the database.

### Layer 3: Persistent Tombstones (`deleted_deployment_ids`) (`src/storage.rs`)
- Added `deleted_deployment_ids: HashSet<String>` to `AppStorage`, persisted to SQLite's `metadata` table under key `'deleted_deployment_ids'`.
- When `remove_deployment()` or `clear_deployment_history()` is called:
  - The record is deleted from SQLite with `rows_affected == 1`.
  - The deleted ID is added to `self.deleted_deployment_ids`.
  - The tombstone set is atomically saved into SQLite's `metadata` table.
- **Startup Defense (`load_or_default`):** Tombstones are loaded from `metadata`. Any records in the `deployments` table matching a tombstone ID are instantly filtered from memory and purged from SQLite via `purge_tombstoned_deployments_from_db`.
- **Background Sync Defense (`sync_from_app_directory`):** When external disk changes are detected (e.g. from an old lingering process writing back stale records), any resurrected deployments matching `deleted_deployment_ids` are rejected from memory and immediately purged from SQLite. A notification is posted:
  `"Prevented X resurrected deployment record(s) from external stale writer and purged from database."`
- **Import Defense (`merge_deployments`):** Drop-in `.json` imports and manual merges ignore any records in `deleted_deployment_ids`.
